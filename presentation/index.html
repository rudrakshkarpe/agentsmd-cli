Why AGENTS.md exists

The coding agent can inspect the repository. The repository does not explain how this team works. The agent guesses, makes a mistake, and needs a correction. The developer records that correction as repository guidance. The next session loads AGENTS.md before work begins. The agent follows the convention instead of repeating the mistake. README.md answers people. AGENTS.md answers coding agents.

AGENTS.md needs an evidence bar

Maintaining agent instructions is already an engineering discipline.

01
Keep it lean

AGENTS.md < 200 lines

02
Don't blindly add rules

Test whether the rule is actually needed.

03
Learn from repeated mistakes

This is already how mature projects think about agent instructions. Our question is: can we make part of this maintenance loop systematic?

The vLLM guidance treats agent instructions as an engineered artifact with token budgets, scope, anti-patterns, and a change checklist. The important lesson is not to add more text. Slide 10 | agentsmd workflow | 1.5 minutes
One task boundary

AGENTS.md update workflow

The coding tool changes. The evidence path stays the same. agentsmd records what changed, what ran, and whether the task succeeded. Reflection returns at most one narrow rule, and often returns no change. The candidate cannot modify AGENTS.md until tests and policy approve it. Approval writes a versioned rule with the run that justified it. Rendering preserves maintainer text and applies only the validated delta.
This slide follows one payload from a coding session to AGENTS.md. Beat 0 names the provider boundary. Beat 1 captures observable session evidence in a run record. Beat 2 produces at most one narrow candidate at the task boundary. Beat 3 shows the only branch: a failed gate keeps the proposal pending. Beat 4 commits an approved rule and its provenance to the ledger. Beat 5 renders only that delta while preserving maintainer-authored text. The bottom line is an audit trail, not another execution path. Capture mechanics vary by provider.
